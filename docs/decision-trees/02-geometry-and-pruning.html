Geometry and Pruning

Chapter 2 of 8. Every split is a horizontal or vertical line in feature space. Every fully-grown tree memorises its training data. Both constraints turn out to have the same fix — and the same cost.

Back up from the scoring function for a moment and look at what a tree looks like in feature space. If your data has two features, each row is a dot in a 2D plane. Each split of the form "is x greater than 5?" becomes a vertical line at x = 5. Each split "is y greater than 10?" becomes a horizontal line. Every leaf corresponds to a rectangle. The tree's prediction for any point is whatever its leaf says.

There are two related things a tree cannot do. It cannot draw a diagonal line. And, on any interesting dataset, it cannot stop before memorising the training data unless you force it to. Both limitations show up geometrically on the same dataset, so we'll fold them into a single interactive that makes both visible.

The superpower: nothing you do to a feature matters

Because a tree only ever compares one feature to a threshold, the only information it uses is the ordering of values, not their magnitudes. Log-transform every value, switch to cents, square-root, standardise — as long as the transformation is monotonic (preserves order), the tree's structure doesn't change one bit.

For most ML models you'd spend a lot of time pre-processing: scaling each feature to unit variance, log-transforming long-tailed ones, one-hot encoding categories. Trees skip all of this. You can feed in raw numbers of wildly different units and the model is happy. This is one of the biggest reasons trees still dominate tabular data.

The blind spot: diagonals

Now for the bad news. If the true boundary between your classes is a diagonal — "positive if x + y > 10" — a tree has to approximate it with a staircase of tiny rectangles. Each step spends some of your data. A few dozen steps and you've exhausted the dataset for what an oblique line would have handled in a single cut.

Oblique trees, invented in 1994, do allow diagonal splits — any hyperplane, at any angle. In theory they solve the staircase problem. In practice they're rarely used, for two reasons. First, finding the best diagonal at every node is computationally much more expensive than sorting one feature. Second, oblique trees lose the magical rank-invariance: scale a feature and your diagonal is wrong, so suddenly you need preprocessing again. The field settled on: accept the staircase.

The overfitting problem, same geometry

Left unchecked, the tree will keep splitting until every leaf contains exactly one training row. On clean data this achieves zero training error — and maximum possible overfitting. The decision boundary becomes a jagged mess that perfectly traces the training set and generalises poorly.

The classical fix is called cost-complexity pruning. You grow the tree all the way, then introduce a single knob α that penalises leaves: the tree's score becomes the training error plus α times the number of leaves. At α = 0 the full tree wins. As α rises, more and more branches get cut back, until at very high α the tree is a single leaf. Somewhere in the middle is the sweet spot where test error is lowest.

Why grow then prune, rather than stopping early? Because early stopping is blind — a mediocre split at depth 3 might enable great splits at depth 4, and early stopping never finds out. Post-pruning sees the whole tree in context before making cuts, so it can keep the promising mediocre split while trimming genuine dead-ends.

You can combine these effects. A 45° boundary is where axis-aligned trees look worst. Now crank up α: the axis-aligned tree sheds many tiny staircase rectangles, leaving only a crude approximation — far worse than the single oblique line would have been. Rotate back to 0° and the axis-aligned tree is fine; the mismatch between data geometry and split geometry disappears, and pruning removes far less error.

Why the staircase persists

The staircase is a symptom of a design choice, not a limitation. If you could fit any linear combination of features at every node — 2x + 3y > 5 — you'd have solved the diagonal problem, but you'd also have left the family of "decision trees" and joined the family of linear models (or, if you chain those linear combinations with sigmoids, the family of neural networks). Trees live at one end of a spectrum: every split is maximally local and discrete. Chapter 7 returns to this and shows what trees look like when you soften that decision.

For pure tabular-data applications, though, the staircase is fine. A thousand staircases combined — which is what the next two chapters show — track any decision boundary, diagonal or not, to arbitrary precision. The trick isn't making one tree smarter. It's making many trees collaborate.

Takeaways

  • Trees split one feature at a time, and only on thresholds. That gives them rank-invariance: any monotonic transformation of a feature leaves the tree unchanged. Log-transform freely.
  • The price is geometric. A 45° boundary forces the tree into a painful staircase. Oblique splits fix this in theory but rarely in practice.
  • A fully grown tree memorises. Zero training error, high variance, poor generalisation. Always needs a stopping rule.
  • Grow, then prune. Cost-complexity pruning with a single α knob. Start at α = 0, raise until test error bottoms out.
  • Pruning beats early stopping. A mediocre split at depth 3 might enable two great splits at depth 4. You only see that with the whole tree grown.
