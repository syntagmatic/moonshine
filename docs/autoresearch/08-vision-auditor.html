The Vision Auditor

Auditing what the viewer actually sees, not what the code says

The current auditor gets HTML and a screenshot but mostly reads the code. It finds duplicate d3.select calls and verbose event handlers because those live in text. It doesn't notice two bars in nearly the same shade, or a label on top of a data point.

The auditor scores what it reads, not what the viewer sees. The gap is where the worst bugs hide.

The gap

A bar chart where one series is fill: "#3b82f6" and another is fill: "#60a5fa": distinct hex values in a text file, indistinguishable on screen at normal viewing distance.

Same class: overlapping labels (different coordinates, colliding text boxes), truncated axes (correct domain, clipped SVG viewport), invisible elements (tooltip in the DOM behind a higher z-index panel). The code is correct, the picture is wrong.

The vision-first pipeline

A vision-first auditor flips the information hierarchy. Instead of reading code and glancing at a screenshot, it analyzes the rendered image without access to the source. The pipeline is straightforward:

The key constraint: the vision model receives only the screenshot and a description of what the visualization should show (the data summary, the intended chart type, the expected number of series). It does not receive the HTML. This forces it to evaluate the output purely as a viewer would.

The test-viz.py pipeline already launches a headless browser and captures PNGs. Routing those to a vision model gives a visual audit.

The text-based auditor stays — it catches code-level issues. The vision auditor runs in parallel on different dimensions.

Comparison auditing

Asking a vision model "rate this chart 1–10" gives inconsistent answers across runs — there is no stable internal caliber for a 7 vs. an 8.

Comparison is more reliable. "Did the visualisation improve?" with two screenshots gets concrete observations: labels no longer overlap, the axis shows the full range, the legend moved out of the data region.

In a loop, the auditor compares each iteration to the previous best. Binary question with supporting evidence: did it get better, and where?

Spatial grounding

Text-based: "the labels may be hard to read." Vision-based: "the label 'Manufacturing' at (340, 28) overlaps the top of the tallest bar." Spatial grounding refers to concrete regions.

The proposer can then act on "move the label at (340, 28) up by 15 pixels" directly, without guessing which label or how far.

A reference-image approach: capture a "golden" screenshot at the start, compare each iteration to it. The model flags exactly which region changed and whether the change looks intentional.

What this changes about autoresearch

Text catches code-level problems. Vision catches rendering-level problems. A block that scores well on text but fails on vision is the category that slips through the current pipeline.

The high-value catches are mundane. Similar colors. Cut-off axis labels. Legends occluding data. Tick density mismatched to range. The vision auditor automates a human reviewer's two-second glance.

The comparison mode is the real leverage. The loop can ask "score went up by 0.1, but did the chart look better?" Some score improvements come from code cleanup that didn't change the output; some score regressions hide visual wins.

Amber risk: Vision models hallucinate spatial locations. A model may report an overlap at coordinates that do not correspond to any element in the image. Resolution dependence is real: bugs visible at 2x rendering may vanish at 1x, and vice versa. Each vision API call costs more than a text call, so adding a vision audit to every iteration increases the per-experiment budget. And there is an uncanny valley of almost-right visual feedback, where the model identifies a real region but mischaracterizes the problem, leading the proposer to make a "fix" that introduces a new bug.

The resolution problem

A retina-obvious bug can be invisible at 1x. A 1px separator renders crisply at 2x DPR but rounds to zero at 1x. A label that fits at 1200px collides with its neighbor at 600px when the layout engine compresses tick spacing. Single-resolution audits miss bugs at other resolutions.

Render at three tiers. Thumbnail (~300px) catches embedded/mobile failures: collapsed labels, overflowing legends, vanishing thin lines. Standard (600px) is the default editing view and catches most layout bugs. Retina (1200px @ 2x DPR) reveals hairline strokes too thin to see, anti-aliasing artifacts, and subpixel misalignment.

No single resolution catches everything. The thumbnail misses subtle color problems; the retina view misses density problems. Merging all three is more complete.

The golden reference pattern

Iteration accumulates drift. A label shifts two pixels, then three, then five. No single delta is large enough to flag. After ten iterations the label sits on top of a data point.

The golden reference catches this. Capture screenshots at all three resolutions at the start. Every iteration compares against this baseline, not just the previous iteration. Cumulative drift gets flagged before it compounds.

The pattern also protects layout. If the initial block has the legend on the right and the title centered, the golden reference encodes that as an implicit constraint. Color and data fixes are fine; layout regressions get caught.

Comparison is structural similarity, not pixel-perfect. Small padding and font shifts are expected; semantic changes are flagged.

Combining text and vision auditors

The two auditors have complementary blind spots. Text catches duplicated selections, missing error handling, magic numbers, non-idiomatic D3. Vision catches color confusion, label occlusion, layout overflow, invisible elements.

Architecture: fork after render. Source goes to text, screenshot goes to vision. Each returns its own dimension scores; the merge produces a composite.

The merge is not a simple average. Some dimensions are text-only (code duplication has no visual signal). Some are vision-only (color distinguishability has no code signal). Some cross-validate: text flags a suspicious viewBox, vision confirms the chart is clipped — agreement boosts confidence.

The text auditor catches ~70% of code-level issues but nearly no rendering bugs. The vision auditor adds a second opinion that covers the rest. One extra API call per iteration to catch a chart that scores 85 on code but renders with two identical-looking series, a clipped axis, and a label hiding behind a tooltip.

The two auditors don't need to agree on a single score. They travel separately. High code / low visual goes back for visual fixes; high visual / low code goes back for refactoring.
