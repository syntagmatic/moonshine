Transfer Learning Across Blocks

How insights from iterating one visualization can accelerate iteration on similar ones

Every block starts cold. The 50th block learns the same lessons the 5th one did — "consolidating color scales breaks density encoding," "removing the charge force collapses the layout" — paid for in API budget and forgotten.

The experiment JSONs from 100+ blocks contain thousands of proposer explanations and audit notes. None of it flows between blocks today.

A lesson from one bee swarm should carry to the next. A color scale fix on parallel coordinates should apply to any block with a similar setup. The question is how.

Four strategies

Four strategies, narrow to broad.

  1. Skill-level transfer. All blocks generated by the same skill share common structure. Parallel coordinates blocks share axis drawing code, brushing logic, path generators. A lesson from iterating one parallel-coords block ("do not remove the brush extent clamp; it prevents selection from escaping the axis") applies to every other parallel-coords block. This is the narrowest form of transfer: same skill, same patterns, same pitfalls.
  2. Pattern-level transfer. Across skills, blocks share code patterns even when the visualizations look nothing alike. Tooltip placement code appears in bee swarms, network graphs, and treemaps. Color scale setup appears everywhere. Axis formatting is universal. When the proposer learns that a particular tooltip refactoring breaks hover interaction, that lesson applies to any block that uses the same tooltip pattern, regardless of skill type.
  3. Failure library. A structured database of "this change failed because..." indexed by pattern type. Before proposing a change, the proposer checks: has a similar change on a similar block failed before? If the library says "removing redundant d3.select calls from axis setup breaks update transitions" and the current block has the same axis pattern, skip that proposal. The library turns individual failures into collective memory.
  4. Meta-prompts. After iterating 10 blocks of a given type, distill the accumulated lessons into a prompt fragment that guides future proposers. "When iterating force-directed graphs, avoid: removing the charge force, consolidating tick handlers, inlining the drag behavior." This is the most compressed form of transfer: hundreds of experiments condensed into a few sentences.

The network

Skill-level transfer in practice

The first of three parallel coordinates blocks tried consolidating axis scale setup into a shared function. Reduced lines, broke per-axis domain clamping. Discarded.

The second hit the same wall. And the third. Three blocks, three wasted experiments. Skill-level transfer would have given blocks 2 and 3 the lesson: don't consolidate per-axis scale setup.

Filter the experiment JSONs by skill tag, group by failure mode → a per-skill transfer corpus.

Pattern-level transfer

Skill-level transfer is narrow. Tooltip placement appears in 70% of blocks regardless of skill; color scale setup and resize handlers are near-universal.

Pattern-level transfer indexes by code pattern, not skill. Extract function signatures and D3 method chains, compute pairwise similarity. Lessons about a tooltip pattern transfer between a bee swarm and a force-directed graph.

Heavier: embed each block (code, audit profile, or both) as a vector and find nearest neighbours. The nearest iterated block becomes the transfer source — its keeps are candidate proposals, its discards are warnings.

The failure library

Every discarded experiment is a data point: a reasonable-looking change, applied to a specific pattern, caught by the audit.

Structure as a lookup table. Key: change type ("consolidate color scales," "inline drag handler"). Value: blocks where tried, pattern context, regressed dimensions. The proposer queries before proposing and skips matches.

The raw material is already in the experiment JSONs. The cost is indexing and keeping the index current.

Meta-prompts

Distill accumulated lessons into a prompt fragment.

Example. "When iterating force-directed graphs: (1) never remove d3.forceCollide or d3.forceManyBody without verifying layout stability; (2) tick handler consolidation breaks when nodes have heterogeneous update logic; (3) extracting link styling into CSS saves lines but breaks dynamic colouring; (4) drag behaviour is load-bearing — don't inline."

Human-readable, auditable, easy to inject into context.

The skill track

Block track compresses files, prompt track improves prompts. The deferred skill track closes the loop: measure quality across all blocks generated by a skill, identify systemic weaknesses, update the skill text.

After 10 iterated blocks the skill absorbs what was learned. After 50 it encodes a map of what works and what doesn't for that visualisation type.

Embedding similarity

Skill tags, pattern signatures, and failure categories all rely on explicit structure. Embedding similarity works without manual indexing.

Represent each block as a vector (source code, audit profile, or both). For a new block, find its nearest iterated neighbours. Their keeps are candidate proposals; their discards are warnings.

The advantage is generality — the embeddings can find that a treemap and a sunburst share more structure than two treemaps with different interaction patterns. The risk is false transfer: two blocks close in embedding space might share d3.scaleOrdinal without sharing deeper patterns.

Risks

False transfer. "Removing the charge force collapses the layout" is true for force-directed graphs and meaningless for radial dendrograms. Noisy similarity makes the proposer waste experiments on inapplicable changes.

Cold start. Transfer requires a corpus. Well-represented skill types have enough; novel ones don't. Two tiers of iteration quality.

Maintenance cost. Failure library needs indexing, deduplication, and pruning as code patterns shift. Meta-prompts go stale after skill rewrites.

Staleness. Meta-prompts crystallise lessons at a point in time. "Avoid inlining drag behaviour" becomes wrong after a refactor that makes drag handlers composable. Need a mechanism to retire stale guidance.

What this changes

Today, 100 blocks costs 100× one block. Transfer bends the curve — the 50th bee swarm starts with the distilled knowledge of the first 49.

Incremental path: start with skill-level transfer (lowest risk). Build the failure library as a byproduct of iteration. Add meta-prompts once a skill has enough iteration data. Save embedding similarity for when scale justifies the infrastructure.

The skill track is the natural home — wiring transfer learning into the instructions that shape every block from the start.

The cold start problem

The first block of a new skill has no transfer data. No failure library, no strategy table, no hit rates. Every experiment is a fresh guess.

Without transfer data, the proposer falls back on generic heuristics — dead code, formatting, nesting. Safe but low-value. A proposer with data from 10 prior bee swarms knows "extract force simulation parameters into a config object" has a 75% keep rate. A cold-start proposer doesn't, and sticks to whitespace.

The gap is measurable. Across our first 50 blocks, the first block of each skill averaged 3.2 experiments before its first ambitious kept change. The fifth block averaged 1.1. Transfer data cuts the exploration phase by ~two-thirds.

Bootstrapping strategies

Three bootstrapping strategies.

Cross-skill priming. Lessons about axis labels, color scale management, and responsive breakpoints transfer across skill boundaries. Weaker than within-skill, better than nothing. "Axis label changes have a 40% discard rate, usually due to contrast or overlap" warms a first parallel coordinates run.

Synthetic seeding. Run 3–5 synthetic experiments covering the major strategy categories before the first real iteration. Costs 5 iterations of budget; populates the failure library and hit-rate table from day one.

Manual priors. A human writes a short briefing: "force layout parameters are sensitive to node count; avoid merging brush and axis drag handlers; highlight-on-hover is safe to refactor." Five minutes of human time, ~10 experiments worth of domain knowledge.
