Random Walks & Effect Systems

A step function's type is not just State → State. It's State → e State, where the effect tag e records what capabilities the function needs to run — and therefore what guarantees you're allowed to expect of it.

§1 · Cold sim

Three walkers, three effect profiles

Three trajectories on the same canvas, three different effect tags. The cyan walker traces a Lissajous curve — the output is a closed-form function of time, so no randomness enters and the effect tag is Det. The purple walker is a lattice random walk reading from a seeded PRNG; its effect tag is Rand (Seed s), and the seed is part of its type. The magenta walker calls Math.random() directly — a reach into the ambient environment, which is IO-flavored Rand with no seed witness.

Press replay: the cyan walker retraces itself because time is deterministic; the purple walker retraces itself because it is reseeded with the same number; the magenta walker draws something entirely new because nothing about its type promised otherwise.

Each trajectory carries an effect strip on its right edge. The active tag is filled; dimmer tags below are capabilities this walker does not need. Det ⊂ Rand ⊂ IO: a less-capable walker can run anywhere a more-capable one is allowed.
Det · closed-form, replayable from t=0 Rand (Seed s) · replayable from s IO / unseeded · not replayable
§2 · Name the types

The effect tag is a compile-time witness of capability

Up to now in this series every step function had the bare shape State → State. That shape is a lie by omission: a walker that reads from Math.random() and one that reads from a seeded generator are indistinguishable at that type. An effect system refines → itself, parameterizing it by a tag e that names which capabilities the right-hand side is allowed to use.

data Det -- no capabilities data Rand -- needs a PRNG data Seed (s :: Nat) -- carries the seed at the type level data IO -- the ambient environment (wall clock, Math.random, ...) type Step e = State -> e State deterministic :: State -> Det State seededWalk :: State -> Rand (Seed 42) State unseeded :: State -> Rand State -- no seed witness; effectively IO

Two readings. First: e is a witness of what the function can do. A value of type Det State proves that the next state was computed without touching any environment — no clock, no entropy, no globals. Second: when e is parameterized (as in Rand (Seed 42)), it is a witness of which run you'll get. Two walkers whose step logic is byte-identical can carry different effect types — and those different types are what let you replay one, audit it, or compose it with others that demand a specific capability.

The subtyping is Det ⊂ Rand (Seed s) ⊂ Rand ⊂ IO. A Det function fits anywhere a Rand one is expected (it simply doesn't use the PRNG); a seeded Rand fits anywhere an unseeded one is expected (it picks a particular run out of the family).

§3 · Signature diagram

The arrow carries a color now

Two signatures stacked. Step Det :: State → Det State on top; Step (Rand s) :: State → Rand s State below. The input pipe is blue (Position — a pair of coordinates is the State). The output pipe's effect band is colored by the effect tag — Det cyan, Rand (Seed s) purple. Capability isn't a runtime flag; it's painted onto the arrow.

The effect strip sits above the output pipe. For Rand (Seed s) the seed s rides along as a compile-time tag beneath the strip — a witness that this arrow picks one specific run out of the Rand family.
§4 · What it lets you say

The replay guarantee, visualized

Here is the empirical content of the effect tag. Top row: two copies of the seeded walker started from the same state with the same seed. Their paths are painted in two hues but they coincide point-for-point — the trajectories are the same mathematical object twice. This is a property of the type: Rand (Seed 42) names one specific walk in the Rand family, so evaluating it twice returns the same path.

Bottom row: two copies of the unseeded walker, started from the same state, same rule, same step size. They diverge immediately — inside the first dozen steps they are already unrecognizable as the "same" walker. This too is a property of the type: Rand without a seed witness makes no promise about which run you get.

Top: Rand (Seed 42) twice — the two paths lie on top of each other. Bottom: Rand (unseeded) twice — they disagree on the very first step. The type is what distinguishes "reproducible" from "not".

The four effects form a poset: Det ⊂ Rand (Seed s) ⊂ Rand ⊂ IO. Every rung up widens the set of programs and weakens the guarantee. Subtyping makes a seeded run usable wherever an unseeded one is expected, but never the reverse — a function that claims Det cannot silently reach for Math.random(). In #11 this rung count becomes the eff axis of the nine-dimensional lattice; the poset is literally one of the coordinates.

§5 · Carry-forward

We added. TV.effectStrip as the new visual vocabulary — capability tags stacked beside a trajectory in the effect palette (Det cyan, Rand purple, IO magenta). The seed-as-type-parameter pattern: Seed (s :: Nat) is a compile-time witness of which run you'll get, not a runtime value buried in a closure. And the reading that an effect tag is a witness of capability — a property the call site can see without looking inside the function.

Reused where. The effect strip returns in #9 when shape becomes a compile-time witness (the same "band next to the arrow" idiom for a different property) and in #10 when traits / contracts become witnesses of what a type can do. In #11 the effect rank — the height of the strip — becomes one axis of the parallel-coordinates view, so every simulation in the series is plotted partly by how much environment it needs.
