Boids

Three simple rules, each a function from Neighbors to Force. The type of a rule and the type of their composition are the same, and that is the whole expressiveness argument.

§1 · Name the types

Newtypes over Vec2

A flock of boids is running below: alignment steers toward neighbors' mean heading, cohesion pulls toward their centre, separation pushes away when too close. The three atomic geometric quantities (Position, Velocity, Force) are all represented as two-component vectors. Without newtypes they'd be interchangeable; with newtypes, the compiler keeps them distinct. Hover a boid to see its record and the three rule-forces acting on it right now.

newtype Position = Position Vec2 newtype Velocity = Velocity Vec2 newtype Force = Force Vec2 data Boid = Boid { id :: BoidId, pos :: Position, vel :: Velocity } type Neighbors = [Boid] type Rule = Neighbors -> Boid -> Force
hover a boid
Hovering a boid reveals its record and draws the three rule-forces leaving it — align, cohere, separate — plus the net Force they sum to. All four arrows share the kind Force; only their origin differs.
§2 · Signature diagram

Three rules, one signature, one combinator

Each rule has the same type. Composition is just their sum, literally vector addition of the three output Forces. Because the input and output types line up, the combinator combine is a one-liner and the compiler vouches for it.

align, cohere, separate :: Rule combine :: [Rule] -> Rule combine rs = \ns b -> sumForces [ r ns b | r <- rs ] sumForces :: [Force] -> Force sumForces = foldr addForce zeroForce
Three pipes converge on the combinator and emerge as one Force. Each pipe also reads the live flock above — a small arrow beside each rule label shows that rule's current mean force, and the output pipe opens into a mini-flock rendering the population it's being applied to.
§3 · What it lets you say

Rule algebra falls out for free

Because Rule has a single uniform type and Force is a monoid under vector addition, rules form a monoid too. Weighted mixes, conditional rules, rules that delegate to other rules: all of them are just more things of type Rule.

weight :: Double -> Rule -> Rule weight k r = \ns b -> scale k (r ns b) near :: Double -> Rule -> Rule near d r = \ns b -> r (filter (within d b) ns) b combine [ weight 1.5 align, cohere, near 20 separate ] :: Rule
1.00 1.00 1.00 flock
Every slider value ends up inside a call to weight k r, returning another Rule. combine takes the list and produces one more Rule. The regime label updates as you mix — same type, different behavior.

Symmetric · hex-wheel

Leader L connects to six followers; the followers form a ring. Aut(G) ≅ D₆, 2 orbits.
|Aut(G)| = 12  ·  orbits = {L}, {F₀..F₅}
leader distinguishes: 1 follower class

Perturbed · + one chord

A single diagonal edge F₀–F₃ breaks the rotation. Aut(G') ≅ 2 × ℤ₂, 3 orbits.
|Aut(G')| = 4  ·  orbits = {L}, {F₀,F₃}, {F₁,F₂,F₄,F₅}
leader distinguishes: 2 follower classes
Node color encodes orbit under the graph's automorphism group — same-color nodes are indistinguishable from the leader's vantage under any consensus-style control. Press broadcast: L's state goes to 1 and followers run a neighbor-average update. Fill intensity tracks each node's current state. On the left the six followers brighten in lockstep. On the right F₀, F₃ — closer to L via the chord — brighten ahead of the outer four, and the two orbits separate visibly.

This is the group-theoretic controllability result from the distributed-agent literature: a multi-agent network's automorphism group is literally the obstruction to distinguishing followers from a central leader. High symmetry ⇒ low controllability; flocking itself is only governable insofar as the interaction graph is asymmetric enough to give a leader purchase. The natural type is Graph tagged with its automorphism group, Graph (Aut g), and a policy whose signature demands distinguishing orbit-equivalent followers fails to typecheck.
