Traffic Flow

When a car is always in exactly one of three states, the state-transition diagram and the Haskell type definition are literally the same picture.

§1 · Cold sim

A ring of cars, and a wave that travels backward

Twenty cars on a circular track. Each is Moving, Braking, or Stopped — no fourth option, no in-between. Tap brake lead car and watch the shockwave crawl against the direction of travel as each driver reacts to the one in front.

The headway between cars shrinks upstream of any braker. A dense-enough ring will jam spontaneously even without the button.

§2 · Name the types

A sum type where the payload depends on the variant

A car's state is one of three constructors. Each carries a different payload — a Speed, a Decel, or nothing at all — and the type of that payload is tied to the variant. You can't ask Stopped for its speed, because there isn't one to ask for.

data CarState = Moving Speed | Braking Decel | Stopped data Input = SeeBrakeLights | ClearRoad | HitZero | LeaderMoves transition :: CarState -> Input -> CarState

This is the kernel of a GADT: a sum where each branch carries its own shape of payload, and a function that pattern-matches on both the state and the input to decide what's next. Only the transitions listed in §4 are reachable — every other pair is simply not in the function's body.

§4 · What it lets you say

The transition diagram is the type

Three nodes, one per variant. Draw an arrow for every transition the step function actually implements. What you get back is identical to the Haskell definition — the shape of the data declaration and the body of transition compressed into a single picture. If a transition isn't drawn, it isn't in the code; if it isn't in the code, a car can't make it.

Nodes are constructors. Edges are clauses of transition. The absence of Stopped → Braking is information: a stopped car cannot decelerate further. The absence of Moving → Stopped is a design choice — every stop passes through braking first.

This is why the pattern scales. A six-state fighter-jet mode selector, a twelve-state TCP connection lifecycle, a hundred-state dialog tree — each is a sum type whose state-transition diagram is literally the type drawn. The visualization is the source of truth, and the code is just its dictation.

The same move covers thermodynamic phase transitions. Magnetite above its Verwey temperature and magnetite below it are distinct structural regimes; the operators that act on one are not meaningful on the other. Encoding this as HighT | LowT with the transition function crossVerwey :: HighT -> LowT makes every phase-crossing a visible event in the type, and every illegal "use the high-T susceptibility past the transition" a compile-time error. The FSM pattern here is the same shape; only the science changes.

Two regimes as two distinct types. The green operators are closed within the Free-flow regime; the red operators are closed within the Jammed regime. nucleate is the only legal crossing — the phase transition lifted into the type system. The dashed refused arrow underneath shows the typing judgment Γ ⊢ accelerate j : ⊥: no derivation exists for applying a free-flow operator to a jammed state. It is the same refusal #1 used for Node Fixed and #7 used for Integrator Euler in a Symp-expecting slot, re-framed as a thermodynamic boundary.

We added. The state-machine-as-sum pattern: a sum type plus a transition function is a directed graph of constructors. Three extension-palette colors (Moving emerald, Braking amber, Stopped red) reserved for car-state variants.
