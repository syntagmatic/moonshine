Springs and Constraints

When every element of a scene is a value of the same sum type, the scene graph is the type tree — and solving the system becomes a single line of fold.

§1 · Cold sim

A soft cloth hangs from its corners

A 5-by-6 grid of particles. Each particle is connected to its neighbors by springs. The top row is held in place by anchors. Under gravity the cloth sags, folds, and — when dragged — stretches in whatever shape the constraint list allows.

Drag a particle. The cloth deforms, and every line you see is an instance of one of three constraint variants.
Spring Anchor Distance
§2 · Name the types

One sum type covers the whole scene

A Constraint is either a Spring, an Anchor, or a Distance. Each variant carries its own payload — the particles it connects, a point to be pinned to, a rest length — but they all share an apply function that nudges the state closer to satisfying it.

data Constraint = Spring ParticleId ParticleId Stiffness Rest | Anchor ParticleId Point | Distance ParticleId ParticleId Length apply :: Constraint -> State -> State

Because every constraint shares one apply signature, the solver has nothing to branch on beyond the variant itself. Pattern-matching on a sum type closes the loop — every case is named, nothing is forgotten.

§3 · Signature diagram

Sum on the left, state through the middle, state out the right

The core function takes one constraint and one state and returns the new state. The sum type is rendered as a fork — three labeled bands, one per variant — feeding into the single apply arrow.

apply :: Constraint -> State -> State solve :: [Constraint] -> State -> State solve cs s = foldr apply s cs
The sum type on the left is TV.sum, rendered for the first time in the series. Any of the three variants can enter the apply socket — the solver doesn't care which, and the type says so.
§4 · What it lets you say

The scene is a list — and a tree

Because all constraints share a type, a scene is just [Constraint]. The solver is a fold. And because variants are named, you can render the whole scene as a tree of typed boxes that mirrors the constraint list exactly. The scene graph is the type tree.

scene :: [Constraint] scene = [ Anchor 0 (Point 100 40) , Anchor 4 (Point 500 40) , Spring 0 1 k L , Spring 1 2 k L , Distance 1 3 D , ... ]
A cut-down version of the cloth's constraint list, laid out as a tree. Each leaf is a typed box colored by its variant. The whole tree is a value of type [Constraint].

The pattern apply :: Constraint -> State -> State is already a group action in disguise. Here the "group" is just the free monoid over a three-element sum — no inverses, no commutation, just a sequence of constraints applied in order. Climb one rung up the series and that free monoid gains structure: in #12 the same signature returns as apply :: Weyl A₂ -> State -> State, where the six elements form a genuine group — S₃, the smallest non-abelian — acting on a six-point root lattice. Sum-apply here, root-system-apply there: the type is unchanged, the underlying algebra gains inverses and relations.
