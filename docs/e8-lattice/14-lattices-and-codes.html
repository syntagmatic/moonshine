E8 as an Error-Correcting Code

Part 14 of 15. Sphere packing and error correction are the same optimization problem. We prove it with a specific example: E8 is what you get when you turn the extended Hamming [8, 4, 4] binary code into a lattice.

Explainer 12 proved that the E8 lattice is the densest 8-dimensional sphere packing. The densest packing is also, structurally, the best error-correcting code in that dimension — the two properties are the same property viewed through different vocabularies. This is not a metaphor: every binary linear code gives rise to a lattice via a procedure called Construction A, every self-dual lattice admits a corresponding code, and the density of the lattice packing equals (up to a standard normalization) the error-correction capability of the code. When we make the correspondence concrete with a specific worked example, the fact that E8 is the densest 8D packing and the fact that the extended Hamming code is the "best" binary [8, 4] code are revealed as the same claim.

This explainer is one example end-to-end. We set up the extended Hamming [8, 4, 4] binary code, walk through Construction A to turn it into an integer lattice in ℝ8, and show that the result, after a standard scaling, is the E8 lattice we have been working with since explainer 3. The reader leaves with a third description of E8 — as roots, as D₈⁺ cosets, and now as an error-correcting code — and sees that the three descriptions agree because they are all the same object.

Packing and error correction as the same question

A binary block code of length n is a subset C ⊆ {0, 1}n — a set of valid "codewords" out of all 2n possible binary strings. When you transmit a codeword over a noisy channel, some bits get flipped; the receiver's job is to figure out which codeword was originally sent. Good codes have the property that codewords are "spread out" in the Hamming metric: no two codewords share too many bits, so a small number of bit-flip errors can always be corrected by finding the nearest codeword to what the receiver saw.

Sphere packing asks a geometric version of the same question. A sphere packing is a set of points in ℝn whose pairwise distances are all at least some minimum value (so that unit spheres placed at each point don't overlap). When noise perturbs a packing point into an arbitrary vector in ℝn, the receiver decodes by finding the nearest packing point. Good packings have the property that packing points are spread out in the Euclidean metric.

The two problems become identical when you connect them through Construction A.

The extended Hamming [8, 4, 4] code

Our worked example is the extended Hamming code, sometimes written [8, 4, 4] or H8. The name encodes three numbers: length n = 8, dimension k = 4 (so there are 24 = 16 codewords), and minimum Hamming distance d = 4 (so any two distinct codewords differ in at least 4 positions). It is self-dual: the code equals its orthogonal complement under the standard bilinear form on 𝔽₂8.

Why the parameters line up

The extended Hamming code's three parameters — length 8, dimension 4, minimum distance 4 — combine to produce the E8 lattice under Construction A in a way that is not coincidence. The argument, step by step:

  1. Construction A gives a lattice in ℤ8.
  2. The lattice's minimum squared length is min(4, d) where d is the code's minimum Hamming distance. For extended Hamming, d = 4, so the minimum squared length is 4.
  3. The number of minimum-length lattice vectors is the sum of (number of integer vectors with ±1 in the "one" positions of each codeword of weight exactly 4) plus (number of integer vectors of squared length 4 whose parity is the zero codeword — these are all-even vectors of squared length 4, e.g. (±2, 0, …, 0)).
  4. Count: 14 codewords of weight 4, each giving 24 = 16 sign choices = 224. Plus 8 positions × 2 signs = 16 from the zero codeword's ±2 vectors. Total: 224 + 16 = 240.
  5. Scale by 1/√2: minimum squared length drops from 4 to 2, matching our earlier description of E8's minimum shell. ✓

The resulting lattice is E8. You could verify this by taking the 240 minimum vectors of (1/√2)·Λ(H₈) and checking that they match the canonical 112 + 128 decomposition we built in explainer 3 — the integer family {±eᵢ ± eⱼ} comes from the 8 positions × 2 signs structure of the zero codeword's minimum vectors, and the half-integer family comes from the weight-4 codewords after the 1/√2 scaling converts ±1 entries into ±½ entries.

This is the third description of E8 in this series. Explainer 3 gave you E8 as "112 integer vectors + 128 half-integer vectors." Explainer 10 gave you E8 as "D8 plus a half-integer coset." Now you have a third description: "Construction A applied to the extended Hamming [8, 4, 4] code, then scaled by 1/√2." All three are exactly the same lattice, arrived at from very different vocabularies: geometric, algebraic, combinatorial.

Decoding as projection

Here is where the "packing = error correction" claim becomes operational. Suppose Alice wants to transmit a codeword of the extended Hamming code to Bob. She encodes the 4-bit message as the corresponding 8-bit codeword, and maps that codeword to the lattice Λ(H₈) via Construction A — specifically, she sends the lattice point whose parity is the codeword and whose non-parity-determined coordinates are zero (so the sent point is a weight-4 vector with ±1 in the "one" positions of her codeword).

The channel adds some real-valued noise. Bob receives a vector y ∈ ℝ8 that is "close to" Alice's lattice point but not exactly equal to it. Bob's decoder finds the nearest lattice point to y — the lattice point minimizing |y − x|2 over x ∈ Λ(H₈) — and reads off its parity pattern modulo 2 to recover Alice's codeword. The decoding succeeds as long as the noise is smaller than half the minimum distance between lattice points — exactly the condition that the noise ball around Alice's point doesn't overlap with any neighbor's ball.

The "error-correcting capability" of the code is exactly the packing radius of the lattice. Denser lattice ⇔ lower error rate. This is what the series has been saying from a new angle: E8 is the densest 8D lattice packing, which means the extended Hamming code is the best 8-bit binary error-correcting code — and by this correspondence, proving either one proves both.

What we take with us

  • Sphere packing and error correction are the same problem. Construction A makes this precise: a binary code becomes a lattice, and the lattice's packing density equals the code's error-correcting capability.
  • E8 from the extended Hamming code. Apply Construction A to the [8, 4, 4] extended Hamming code, scale by 1/√2, and the result is exactly the E8 lattice.
  • Three descriptions of E8. Roots (112 integer + 128 half-integer), D₈⁺ cosets, and Construction A on extended Hamming. All the same object.
  • Lattice-code dictionary. Every coding-theoretic concept has a lattice-theoretic twin. Self-dual ⇔ unimodular. Weight enumerator ⇔ theta series. Decoder ⇔ nearest-lattice-point lookup.
  • Further reading. For the Leech-lattice analog using the binary Golay [24, 12, 8] code and Construction B, see Conway & Sloane, Sphere Packings, Lattices and Groups, chapters 3–5.
