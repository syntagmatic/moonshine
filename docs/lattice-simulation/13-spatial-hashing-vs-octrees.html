Spatial Hashing vs Octrees

Part 13 of 15. A lattice does not have to represent physical space. It can be a data structure — a bucket grid that collapses quadratic neighbour-search into something sublinear. Uniform (hash) and hierarchical (quad/octree) variants sit on the two ends of the same spectrum.

Every physical simulation that got built on an explicit lattice in Acts I–IV paid for the lattice with memory: one entry per site, whether that site contains anything interesting or not. The payoff was that the lattice encoded a symmetry of the continuum — translation, rotation, the point group — and the discretisation inherited it. This final act turns the trade on its head. Here the lattice is not a model of space, it is a trick for finding neighbours fast.

Consider N particles in a box, each with a position, and the question: for every particle, which other particles lie within distance r? Boids, smoothed-particle hydrodynamics, Lennard-Jones molecular dynamics, collision detection in a physics engine, density estimation, k-nearest-neighbour classification — the same kernel appears in all of them. The naive algorithm compares every pair:

This is O(N2). At N = 104 particles you do 108 distance checks per frame; at N = 106 you do 1012. That is unaffordable for anything that needs to run interactively, and it is the price a simulation pays for having no indexing structure. The fix is to overlay a lattice onto the point set and use the lattice to prune distant pairs before any real distance check happens.

Spatial hashing: a flat uniform lattice

Pick a cell size s at least as large as the query radius r. Overlay an infinite uniform grid on the plane. Each particle with position (x, y) sits in the cell with integer index

Store the set of particles in a hash table keyed by (i, j). Insertion is O(1) per particle: compute the index, append to the bucket. Query for a radius-r neighbourhood around a point p is also cheap — at cell size s ≥ r the neighbourhood fits inside p's own cell plus the eight adjacent cells, so you only need to check those 3×3 = 9 buckets. If particles are distributed uniformly with density ρ, each bucket holds ρs2 particles in expectation, and total query cost is O(ρs2) — constant, independent of N. Sweeping this query over all N particles is O(N).

The lattice as equivalence relation. A spatial hash is nothing more than the quotient of ℝ2 by a uniform lattice: two points are equivalent if they land in the same cell. The fact that the lattice is translation-equivariant — a hallmark of Act I — is what makes queries cheap, because the 3×3 neighbour pattern is the same everywhere. The "group" here is just ℤ2, but acting on a data structure instead of a physical state.

Quadtrees: a recursive adaptive lattice

A quadtree drops the uniformity. Start with a single cell covering the whole domain and a capacity k. Insert points one at a time. When a cell exceeds capacity, subdivide it into four equal quadrants and re-insert the points into whichever child contains them. Recurse as needed. The result is a tree whose leaves are cells each holding at most k points — except in the pathological case of coincident points, which can force arbitrary depth.

Build cost is O(N log N) on reasonable distributions, because each point walks from root to leaf and the depth of the tree grows like log4 N. Query for a radius-r neighbourhood descends the tree, pruning any subtree whose cell is strictly farther than r from the query point. The expected cost is O(log N + k), where k is the number of reported matches. Sweep over N particles: O(N log N).

The critical difference from the hash is adaptivity. Where points are sparse, a single leaf covers a large region and the tree has few nodes there. Where points are dense, the tree subdivides all the way down until each leaf is at the capacity cut-off. A hash grid with cell size s cannot react to this: if it is sized for the dense region it wastes memory on empty cells in the sparse region, and if it is sized for the sparse region each dense cell overflows and the query degrades to linear in bucket size.

What the picture shows

Three things to look for. First, turn the distribution to uniform and the hash grid's "particles examined" is nearly identical to the quadtree's — both structures are doing essentially constant work per query, and the hash wins on constants because it skips the pointer chases. Second, switch to clustered. The hash grid's examined-count spikes wherever the cursor enters a cluster cell; the quadtree's stays bounded because its leaves subdivided exactly down to capacity. Third, watch the bottom row: the hash has thousands of uniform-size buckets (most of them empty in the clustered case), while the quadtree has a much smaller number of leaves concentrated where the data is.

Push the query radius r past the hash cell size s. The 3×3 neighbourhood is no longer enough — neighbours can sit two cells away — and the algorithm has to scan a 5×5 or 7×7 block instead. The examined-count scales as (2⌈r/s⌉+1)2. This is why one picks s roughly equal to r: smaller s wastes memory on buckets, larger s wastes work on distant particles.

Memory, updates, and rebuilds

The comparison is not only about query time. In a dynamic simulation — boids, SPH, a physics engine — particles move every frame, and the indexing structure has to keep up. Here the hash has a decisive advantage: a particle's bucket is a pure function of its position, so moving it is O(1) (remove from old bucket, re-insert into new). A quadtree has no such locality. A moved point may force a leaf split or merge, and naive implementations rebuild the tree from scratch each frame. The rebuild is O(N log N) again, which on modern CPUs often wins anyway because the tree is cache-friendly, but the engineering effort to do it correctly is real.

Memory scales differently as well. A hash grid spanning an L × L domain with cell size s stores O((L/s)2) buckets, independent of how many particles occupy them. A quadtree stores O(N) nodes, proportional to the actual data. Large sparse domains favour the tree; small dense domains favour the hash.

Bounding volume hierarchies

Collision detection in a physics engine is the same problem with a small twist: the objects are not points but axis-aligned bounding boxes (AABBs), and the query is "which pairs overlap?" rather than "which pairs are within r?" Spatial hashes still work — hash each AABB into every cell it touches — but hierarchical structures outperform them, because boxes vary wildly in size. The industry standard is the bounding volume hierarchy (BVH), a binary tree whose internal nodes each store an AABB containing all the leaf AABBs below them. Query descends the tree, pruning any subtree whose parent AABB does not intersect the query. A BVH is what a ray tracer uses; it is what Box2D, Bullet, and PhysX use for broad-phase collision; it is the same idea as an octree, only the split axis is chosen adaptively instead of always bisecting in the middle.

Connection to the lattice theme

The spatial hash is a uniform lattice. Its bucket indices live on ℤ2; its cells are the fundamental domain of the translation group ℤ2 acting on ℝ2. Shifting every point by a lattice vector gives back the same hash table, re-indexed — the structure is translation-equivariant in exactly the sense of Act I. The query kernel (3×3 neighbours) is the same at every cell, because the lattice has no preferred origin.

The quadtree is also a lattice, but a non-uniform one. Each leaf is a cell of the 2-adic lattice (ℤ2)2 truncated at some depth, and descending the tree corresponds to refining the 2-adic distance between points. The non-uniformity is the whole point: it lets the lattice react to the data rather than forcing the data into a prescribed grid. A BVH is the same idea with the splits chosen by a cost heuristic rather than by bisection.

Both structures have collapsed an O(N2) problem — exhaustive pairwise comparison — into sublinear-per-query work, by imposing a lattice on the data and asking questions modulo that lattice. The lattice is no longer a model of physical space; it is a compiler trick. But the mathematics of translation groups, fundamental domains, and cell-wise equivariance that carried Acts I–IV carries this too, and that shared vocabulary is why the trick generalises from 2D billboards to 3D fluid simulation to 6D motion-planning configuration spaces without modification.

The unifying move. Every algorithm in this explainer works by replacing "for each pair of points, do something" with "for each cell, do something with the points in it and its neighbours". The cell structure — the lattice — is what makes the outer loop cheap. Whether that lattice is flat (hash) or recursive (tree) is an engineering choice about density and dynamism; the underlying substitution of all pairs with cellwise loop is what buys the speedup.

Takeaways

  • All-pairs is unaffordable. Naive O(N2) distance checks break past N ≈ 104. Every N-body code uses some spatial index.
  • Spatial hash = uniform lattice. Cell size s ≥ r; bucket index floor(x/s). Insert O(1), query scans 3×3 cells, total O(N) at uniform density.
  • Quadtree / octree = recursive lattice. Build O(N log N); query O(log N + k). Adapts to clusters; each leaf at bounded capacity.
  • Hash wins on uniform, dynamic, cache-heavy workloads. Tree wins on clustered, sparse, large-domain workloads.
  • BVH is the octree of bounding boxes. Collision detection and ray tracing live here.
  • The lattice is a compiler trick. The same translation-equivariant machinery from Acts I–IV makes the query cheap, but now the lattice indexes data, not physics.
